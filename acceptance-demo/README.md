# 验收指标怎么来 —— 可运行实证

> 回答一个具体问题：**乙方交付一堆程序，验收平台怎么确定那三个指标？**
> 这个目录里的代码是真实可跑的，不是示意。

## 核心答案

**指标不是"读"代码读出来的，是"跑"代码跑出来的。**

平台不可能靠理解代码给出客观分数——那还是 AI 主观判定。唯一的办法是平台自己把代码跑起来，然后测量可观测的输出。

三步：

| 步骤 | 做法 | 产出 |
|---|---|---|
| 1 | 平台按 **commit hash** 检出交付物，跑**规格指定的**测试命令 | 必测用例通过率 |
| 2 | 平台**自己启动**这份代码，多轮探测接口 | 接口可用率 |
| 3 | 比对响应字段与**锁定的契约** | 契约字段覆盖率 |

## 运行

```bash
# 跑一次完整验收
node harness/acceptance-harness.js

# 跑四个对照实验（验证平台是否真能发现问题）
node harness/experiments.js
```

无依赖，Node 即可运行。

## 三个指标的实际来源

**① 必测用例通过率**

跑 `node test/run-tests.js --suite=required`，解析输出的 JSON 报告：
```
passRate = passes / (passes + failures)
```
关键是 `--suite=required` —— 只统计**必测组**。测试命令写在验收规格里，**乙方无法更改**，也就无法通过"删掉失败的用例"来提高通过率。

**② 接口可用率**

平台在随机端口启动交付物，跑 N 轮 × M 个端点：
```
availability = 成功探测数 / 总探测数
```
关键：**接口地址由平台生成**，不存在"甲方提供一个接口地址"这种配置项，所以甲方自建假接口这条路在架构上就不成立。

**③ 契约字段覆盖率**

```
coverage = 实际响应 ∩ 契约必填字段 / 契约必填字段总数
```
关键是**分母来自契约**。乙方多返回字段无法提高覆盖率——分母不动，分子增加也是有限度的。

## 四个对照实验的实测结果

| 实验 | 注入的问题 | 平台能否发现 |
|---|---|---|
| **A** | VIP20 折扣算错（八折写成九折） | ✓ 通过率从 100% 降到 90%，精确定位到失败用例 |
| **B** | 乙方把 3 条失败用例标记为 extra（逃出统计） | ✓ 实测 7 条 ≠ 约定 10 条，判定无效交付 |
| **C** | 甲方伪造验收环境 | ✓ 架构上不可能——平台自建环境，无可伪造第三方 |
| **D** | 响应漏掉 `currency` 字段 | ✓ 覆盖率 85.71%，指出 `/orders/A001 → currency` |

实验 A 的实际输出：
```
失败用例    : applyDiscount: VIP20 打八折
平台是否发现 : ✓ 发现并精定位到用例
```

实验 D 的实际输出：
```
字段覆盖率  : 85.71%
缺失字段    : /orders/A001 → currency
```

**平台不只说"不通过"，而是精确指出哪个接口少了哪个字段。**

## 一个重要的实测发现

第一版交付物里，我故意留了个 bug：`GET /orders/:id` 在订单不存在时返回 200 而非 404。

**平台没测出来** —— 因为探测清单里没有这个端点。

```
平台只测规格里列的端点，测不到没列的。
```

这不是缺陷，而是**验收规格必须签约定死**的直接证据。如果甲方在签约时把规格写全，平台就能测到；如果规格漏了，平台就测不到。

**这回答了"验收指标怎么来"的最后一层**：指标的质量取决于验收规格的质量，而规格由双方在签约时共同锁定并写入链上。

## 平台测不到的部分（必须人来看）

- 规格清单外的接口 / 场景
- 代码是否优雅、命名是否清晰、可维护性
- 架构是否合理、有无隐藏后门（可辅以静态扫描 + 人工评审）

**这正是"范围克制"的意义**：只对能被客观验证的部分做自动验收，其余明确交给人工判断，而不是伪装成自动化。

## 工程踩坑

| 问题 | 原因 | 解法 |
|---|---|---|
| `fs.cpSync` 导致进程崩溃 0xC0000409 | 该 Node 版本上不稳定 | 手写递归 `copyDir` |
| `__dirname` 在部分运行态为 undefined | 打包/单文件运行 | 改用 `process.cwd()` |
| spawn 子进程未清理导致父进程崩溃 | Windows 句柄残留 | 统一登记 + `process.once('exit')` 强制 kill |
| 探测失败时输出 `undefined` | 错误分支没填字段 | 每个失败分支都返回完整结构 |

## 与 Web3 方案的关系

这套采集逻辑与 `web/assets/engine.js` 和 `DeterministicEvaluator.sol` 的判定逻辑完全一致：

```
weighted = (test×wTest + api×wApi + field×wField) / 10000
score    = (weighted + 50) / 100
passed   = gateTest && gateApi && gateField && score >= threshold
```

实测得到的三个数字（万分比）直接喂给链上评估器，判定在链上完成。事实报告哈希上链后，任何人都能用**同一 commit + 同一规格**重跑并验证结论一致。
